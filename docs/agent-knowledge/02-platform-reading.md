# Agent 阅读版：怎样真正读懂一个平台

## 1. 任务与边界

当创作者要理解一个平台、比较入口，或判断某个内容承诺能否在平台上被目标观众发现时，使用本协议。目标是产出一份能支持具体创作决策的平台阅读简报，而不是平台百科、算法猜测或成功率预测。

本站人类文章提供共同框架；七个平台的现行事实要回到第二部分各自的长文及其来源核验。这里没有提供实时平台数据。本协议中的观察方法是项目工作法，不是经过代表性样本验证的行业标准。

Agent 不得假设自己能读取网站页面状态、浏览器账号、访谈答卷、用户私有统计或平台后台。执行环境没有浏览能力时，向创作者索要可公开来源或记录所需的界面观察；不能声称查过当前页面。不得要求账号密码、绕过访问控制或收集与判断无关的个人信息。

## 2. 先锁定决策问题

开始检索前，把问题改写为以下结构，并向创作者核对关键空项：

- 平台及具体产品界面：例如主 App、创作者后台、搜索结果页或某一内容形态。
- 创作者当前要做的决定：选择主阵地、设计栏目、判断某条内容的入口，还是核对一项规则。
- 目标观众与场景：谁在什么时刻完成什么任务或寻找什么体验。
- 内容对象：题材、承诺、形态和大致生产条件。
- 比较范围：单平台的哪条路径；或同一时间、同一任务下的多个平台。
- 决策时点：规则需在什么时候有效；长期结构观察涵盖哪段时期。
- 已有资料：档案中与本判断有关的产能、偏好、目标、边界，以及创作者提供的作品、截图或数据。

缺少目标观众、内容对象或决策时，不要先生成“适合/不适合”的结论。可以先解释需要哪些观察，再把未知项列出。不要为了走完整流程而要求重建整份创作者档案。

## 3. 建立来源账本

开始核验前先查 `docs/claims/registry.json`，复用已有 claim_id、范围与状态；若新来源改变已有判断，按该记录的消费者清单逐项修订文章、经验卡、协议和 skills，再运行 `npm run check`。本登记目前只覆盖首批 P0 主张。

每个会影响建议的事实单独分配 claim_id，并留下支持材料：

| 字段 | 要求 |
| --- | --- |
| claim_id | 简短稳定的编号，供简报、反例和更新引用。 |
| 原子主张 | 一句话只表达一个可检查的事实或解释。 |
| 状态 | 官方可核实事实、直接观察、创作者自述、整理、推断、假设或未知。 |
| 来源 | 原始页面、文件或样本记录的标题与直接链接；引用截图时给出文件名或定位。 |
| 时间 | 来源发布日期/更新时间、Agent 核验日和观察时点；找不到就写未知。 |
| 范围 | 适用平台版本、地区、语言、账号类型、内容类别和入口。 |
| 支持与反例 | 精确指向支持片段；记录冲突材料和可能的替代解释。 |
| 决策影响 | 该主张会改变创作者的哪项选择；没有影响的材料不必堆入简报。 |

取证顺序：

1. **规则与功能定义**：优先查平台官方帮助、规则、产品公告或创作者说明。打开原始页面，核对适用对象和更新时间。搜索摘要、转载和讲解视频只能作为线索。
2. **公开研究**：记录研究对象、时间、地区、样本和方法。研究只支持其设计所覆盖的范围；不能把早期调查直接说成当前全体用户状态。
3. **界面观察**：写明入口、查询词或路径、日期时段、账号状态、应用/页面版本、样本单位和采集方式。对登录账号的观察受个性化影响；若无法控制条件，明确这一限制。
4. **创作者案例**：只记录可追溯的原始表述和公开指标，并注明账号阶段、时期、内容、指标是否可见。单个案例用于产生假设，不证明普遍规律。
5. **项目整理和推断**：整理必须可回溯到原始记录。推断必须标状态、依据、反例、适用范围和下一项核验任务。Agent 自身记忆或语言置信度不是来源。

当浏览工具可用且问题涉及现役规则或功能时，查官方原文并给可点击来源；不可用时，交付待查清单与暂定边界，不得伪装成已核验。来源互相冲突或已失效时，保留冲突。

## 4. 按路径观察，不把入口混成算法

把平台拆成四个可见环节：

1. **进入**：观众主动搜索、从关注关系进入、接收分享、浏览推荐或参加活动。一次观察只描述一个入口。
2. **遇见内容**：记录内容主题、标题/封面承诺、形态、时长或篇幅、发布时间及内容被放置的位置。
3. **消费和反应**：只抄录观察者实际能看到的完成、互动、评论、收藏、关注或后续行为。看不到的后台数据写“不可见”。
4. **后续关系**：记录观众能否继续追更、回访、咨询或进行平台允许的交易；区分功能存在、创作者符合条件、观众实际采用这三件事。

观察前定样本单位及停止条件。若目标只是发现表达类别，可做同条件的探索性小样；样本数量按本轮问题、差异、预算和停止条件解释；不存在固定条数即可讨论总体比例的门槛。便利样本不能代表平台整体。入口、账号状态或时间不同的记录不得合并计算比例。写比例时同时写分子与分母；样本不足则报数量和边界，不硬凑百分比。

观察中同时寻找反例。若某主张是“入口 X 里的样本更常给出步骤承诺”，要问是否由查询词、结果排序、样本时间或账号个性化解释。若不能排除，主张降为该样本的描述。不得从浏览量或互动关联反推推荐权重，也不得将创作者可见指标解释成收入、转化或完播。

## 5. 从材料走到建议

每条建议都要沿同一条链说明：

- **平台事实**：产品或规则具体支持什么；引用来源和时间。
- **观众任务**：目标观众的情境与证据；分清研究结果、观察和假设。
- **内容动作**：创作者可以改变什么，例如开头、信息次序、演示、标题承诺、更新节奏或互动方式。
- **个人条件**：该动作是否符合创作者的产能、表达意愿、目标回报和边界；只使用相关且经确认的档案字段。
- **代价与未知**：时间、技能、版权、隐私、资质、商业及关系成本；未证实之处明列。
- **验证方法**：下一条低成本观察或试作能区分哪些解释，观察对象、记录项、时间窗和改判条件是什么。

把不可控的内部排序权重从建议里剔除。可以说“该入口公开支持关键词检索，值得检查你的目标词下出现什么内容”；不能说“平台偏爱关键词内容”，除非有适用范围明确的可验证证据，并且没有把相关性冒充因果。

比较平台时使用共同的观众任务、内容承诺、观察时期和可比证据。表格单元应标出其来源状态，不可比的格子写“不适用/未知”，不要用总分填补。匹配矩阵只生成候选；个人选择还需承受成本、垂域调查和实际试作。

## 6. 建议输出结构

用下面的 Markdown 结构交付。没有材料支撑的部分保留“未知”，不要用流畅文字补齐。

### 平台阅读简报

- 决策问题：
- 平台/具体界面/版本：
- 目标观众、场景与内容承诺：
- 观察时期、地区、语言与账号条件：
- 资料覆盖与重要缺口：

#### 路径图
进入 → 遇见 → 消费/反应 → 后续关系。每一环分别写已知、来源状态与未知。

#### 主张账本
每项包括 claim_id、原子主张、状态、来源与日期、范围、反例/替代解释、决策影响。

#### 创作者变量
| 可调整动作 | 支持材料 | 预计代价 | 还需本人确认 |
| --- | --- | --- | --- |

#### 候选解释与反证
最多列出真正会改变当前决定的解释；每个解释附支持记录、反例和下一项核验任务。

#### 条件式建议
写成“在条件 X 成立时，先做动作 Y；到时间 T 检查信号 Z。若出现结果 R，则调整或停止”。不要写成功率或收益承诺。

#### 未知与复查
列出阻止当前结论的未知、责任人、官方核验入口/观察任务和下次复查日。

## 7. 质量检查与停止条件

交付前逐项检查：

- 每个现役规则、门槛和功能是否有直接来源、核验日期及适用账号范围？
- 界面样本是否写了入口、账号条件、日期、样本单位与分母？
- 观察、可核实事实、自述、整理、推断、假设和未知是否分栏？
- 是否把相关性误写成算法因果，或把一个案例说成平台常态？
- 个人适配是否引用了创作者确认过的档案字段，而非人格标签或擅自画像？
- 是否写出代价、反例、未知和能推翻当前建议的信号？
- 不同平台的比较是否使用相同任务、内容对象与时间范围？

遇到以下任一情形，停止扩大结论并降低输出级别：当前规则找不到原文；官方来源过期或相互冲突；观察条件无法说明；样本只来自单一爆款或个性化账号首屏；关键指标不可见；不同解释无法区分。此时可以输出路径框架、有限样本描述、待查清单或试作设计，但结论标记为“暂不能判断”。
